## 문을 달았는데 왜 아무도 못 들어올까요?

VPC에 인터넷 게이트웨이를 붙이고, 퍼블릭 서브넷이라고 이름 붙인 곳에 웹 서버를 띄웠습니다. 그런데 브라우저에서는 접속이 안 됩니다. 문은 분명 달았는데 길이 없는 걸까요?

## 인터넷 게이트웨이는 문, 라우팅 테이블은 길 안내

**인터넷 게이트웨이**(IGW)는 VPC와 인터넷 사이의 문입니다. 쓰려면 두 단계가 필요합니다.

1. **Attach**: 인터넷 게이트웨이를 VPC에 붙입니다.
2. **Associate**: `0.0.0.0/0 → 인터넷 게이트웨이` 경로를 가진 **라우팅 테이블**을 서브넷에 연결합니다.

라우팅 테이블은 "이 목적지로 가는 트래픽은 저기로 보내라"는 규칙 표입니다. `0.0.0.0/0`은 "VPC 안이 아닌 모든 곳"을 뜻합니다. 앞의 웹 서버는 1단계만 하고 2단계를 빠뜨린 상태였습니다.

| 서브넷 | 라우팅 테이블의 0.0.0.0/0 | 결과 |
| --- | --- | --- |
| 퍼블릭 | 인터넷 게이트웨이 | 인터넷과 양방향 통신 |
| 프라이빗 | NAT 게이트웨이 | 밖으로 나가는 연결만 가능 |
| 프라이빗 | 경로 없음 | VPC 안에서만 통신 |

퍼블릭 서브넷의 EC2가 인터넷에서 보이려면 **퍼블릭 IP**(또는 탄력적 IP)도 있어야 합니다. 프라이빗 IP만으로는 인터넷에서 찾을 수 없습니다.

## 프라이빗 서브넷도 밖에 나가야 할 때가 있다

프라이빗 서브넷의 서버도 OS 패치(`apt update`), 결제 API 호출, 라이브러리 다운로드처럼 바깥에 나갈 일이 있습니다. 이때 **NAT 게이트웨이**를 퍼블릭 서브넷에 두고, 프라이빗 서브넷의 라우팅 테이블을 NAT로 보냅니다. NAT는 안에서 시작한 연결의 응답만 돌려보내므로 바깥에서 먼저 들어오는 길은 여전히 막혀 있습니다. 관리형이라 편하지만 켜져 있는 시간만큼 비용이 나갑니다.

## 관리자가 들어가는 길과 S3로 가는 지름길

- **Bastion 호스트**: 퍼블릭 서브넷에 둔 관리용 서버입니다. 관리자는 Bastion에 SSH로 접속한 뒤 프라이빗 서브넷의 서버로 들어갑니다.
- **VPC 엔드포인트**: S3와 DynamoDB는 **게이트웨이 엔드포인트**를 라우팅 테이블에 추가하면 NAT 없이 AWS 내부망으로 접근할 수 있습니다. 무료이고 인터넷을 거치지 않습니다.

<LessonSummary>

인터넷 게이트웨이는 VPC에 붙이고(Attach) 라우팅 테이블로 서브넷에 연결해야(Associate) 쓰입니다. `0.0.0.0/0`이 인터넷 게이트웨이로 가면 퍼블릭, NAT로 가면 밖으로만 나가는 프라이빗 서브넷입니다. 인터넷에서 보이려면 퍼블릭 IP도 필요합니다.

- 접속이 안 되면 퍼블릭 IP → 라우팅 테이블 → NACL → 보안 그룹 순서로 의심합니다.
- S3는 게이트웨이 엔드포인트로 NAT 없이 접근할 수 있습니다.

</LessonSummary>
