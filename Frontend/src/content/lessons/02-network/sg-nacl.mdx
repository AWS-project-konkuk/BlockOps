## 443을 열었는데 왜 막혔을까요?

웹 서버의 보안 그룹 인바운드에 HTTPS 443을 추가했습니다. 그런데 요청은 여전히 서버에 닿지 않습니다. 보안 그룹 말고 또 누가 문을 지키고 있는 걸까요?

## 두 검문소의 위치가 다르다

VPC에는 검문소가 두 곳 있습니다. 요청은 **서브넷 경계의 NACL**을 먼저 지나고, **인스턴스 앞의 보안 그룹**을 그다음에 지납니다. 앞의 문제는 서브넷의 NACL이 443을 거부하고 있었던 경우입니다. 보안 그룹이 아무리 허용해도 NACL에서 막히면 닿지 않습니다.

| 구분 | 보안 그룹 | 네트워크 ACL |
| --- | --- | --- |
| 적용 위치 | 인스턴스(ENI) | 서브넷 |
| 상태 | Stateful: 들어온 요청의 응답은 자동 허용 | Stateless: 응답도 따로 검사 |
| 규칙 | 허용만 | 허용과 거부 |
| 평가 순서 | 모든 규칙을 함께 검토 | 규칙 번호가 낮은 것부터, 처음 맞는 규칙 적용 |
| 기본값 | 인바운드 모두 차단, 아웃바운드 모두 허용 | 모두 허용 |

## Stateless는 응답도 다시 검사한다

NACL은 응답을 기억하지 않습니다. 클라이언트가 443으로 요청하면 서버의 응답은 클라이언트의 **임시 포트**(1024~65535 중 하나)로 나갑니다. NACL 아웃바운드에서 이 범위를 막으면, 들어오는 요청은 허용했어도 응답이 나가지 못합니다. 보안 그룹은 Stateful이라 이런 걱정이 없습니다.

NACL은 규칙 번호 순서가 중요합니다. 100번 규칙에서 거부되면 200번에 허용이 있어도 막힙니다.

## 보안 그룹은 다른 보안 그룹을 가리킬 수 있다

서버가 늘어날 때마다 IP를 규칙에 추가하는 건 번거롭습니다. 보안 그룹 규칙의 출발지에 **다른 보안 그룹**을 적을 수 있습니다. 예를 들어 DB의 보안 그룹은 "웹 서버 보안 그룹에서 오는 5432만 허용"으로 두면, 웹 서버가 몇 대가 되든 규칙을 고칠 필요가 없습니다. 이를 **보안 그룹 체이닝**이라고 합니다.

## 접속이 안 될 때 의심하는 순서

1. **퍼블릭 IP**: 인터넷에서 찾을 주소가 있는가
2. **라우팅 테이블**: 0.0.0.0/0이 인터넷 게이트웨이로 가는가
3. **NACL**: 서브넷 경계에서 인바운드·아웃바운드(임시 포트)를 막지 않는가
4. **보안 그룹**: 인스턴스가 그 포트를 허용하는가

<LessonSummary>

보안 그룹은 인스턴스 앞에서 허용 규칙만으로 검사하고, 들어온 요청의 응답은 자동으로 내보냅니다. NACL은 서브넷 경계에서 허용·거부를 규칙 번호 순서로 검사하고, 응답 방향도 따로 봅니다. 요청은 NACL을 먼저 지나므로 보안 그룹이 허용해도 NACL이 막으면 닿지 않습니다.

- 접속 문제는 퍼블릭 IP → 라우팅 → NACL → 보안 그룹 순서로 좁혀 갑니다.
- DB 같은 내부 자원은 IP 대신 보안 그룹 체이닝으로 허용합니다.

</LessonSummary>
