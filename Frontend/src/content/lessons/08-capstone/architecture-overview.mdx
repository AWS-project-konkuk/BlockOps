## 지금까지 배운 서비스를 한 장에 그리면?

1단원부터 7단원까지 S3, CloudFront, VPC, ALB, Auto Scaling, RDS, SQS, SNS, ECS, Lambda, DynamoDB, Prometheus를 배웠습니다. 이 서비스들은 쇼핑몰 하나 안에서 어떻게 이어질까요? 그리고 주문이 실패하면 어디부터 봐야 할까요?

## 네 갈래 경로로 나눠 보기

| 경로 | 흐름 | 관련 단원 |
| --- | --- | --- |
| 정적 파일 | 사용자 → Route 53 → CloudFront → 비공개 S3(OAC) | 1단원 |
| 요청 | 사용자 → Route 53 → 인터넷 게이트웨이 → ALB → 프라이빗 서브넷의 ECS·ASG → RDS(Multi-AZ) | 2·3·5단원 |
| 비동기 | 주문 서비스 → SNS → SQS(FIFO·표준) → Lambda → DynamoDB | 4·6단원 |
| 관측 | 컨테이너 지표 → Prometheus(Pull), Lambda·AWS 지표 → CloudWatch(Push) | 7단원 |

각 경로는 서로 다른 문제를 풉니다. 정적 파일은 캐시로 가깝고 싸게, 요청은 여러 가용 영역에 나눠 멈추지 않게, 비동기는 느린 일을 떼어 놓아 주문이 막히지 않게, 관측은 문제가 생겼을 때 어디인지 알게 합니다.

## 장애는 요청 경로를 따라 찾는다

주문이 DB에 들어가지 않을 때는 요청 경로를 **앞에서부터** 따라갑니다. 처음 실패한 지점이 원인일 가능성이 가장 큽니다.

1. **이름과 문**: Route 53이 맞는 곳을 가리키는가, 인터넷 게이트웨이와 라우팅 테이블이 있는가 (2단원)
2. **로드 밸런서**: 리스너 프로토콜이 맞는가, 헬스 체크 경로가 앱에 있는가 (3단원)
3. **실행 자원**: 프라이빗 서브넷에서 이미지를 받을 바깥 경로가 있는가, 태스크 역할이 맞는가 (5단원)
4. **보안 그룹**: 앞 단계의 보안 그룹에서 오는 요청을 허용하는가 (2단원)
5. **DB**: 프라이빗 서브넷에 있는가, Multi-AZ로 장애를 버티는가 (3단원)

다음 실습에서는 이 순서대로 장애 세 가지가 섞인 주문 서비스를 진단합니다.

<LessonSummary>

1~7단원의 서비스는 정적 파일·요청·비동기·관측 네 경로로 나눠 보면 하나의 아키텍처로 이어집니다. 각 경로는 속도와 비용, 가용성, 느슨한 결합, 원인 파악이라는 서로 다른 문제를 풉니다. 장애는 요청 경로를 앞에서부터 따라가며 처음 실패한 지점에서 찾습니다.

- 정적 파일은 CloudFront + 비공개 S3, 요청은 ALB + 멀티 AZ, 느린 일은 큐, 지표는 실행 방식에 맞는 수집 경로로 보냅니다.
- 실패 메시지가 가리키는 지점의 단원 규칙을 먼저 확인합니다.

</LessonSummary>
