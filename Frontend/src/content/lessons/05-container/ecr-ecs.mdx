## 로컬에서 만든 이미지를 AWS에서 열 개 띄우려면?

Docker 이미지 `app:v2`를 노트북에서 만들었습니다. 이제 AWS에서 이 이미지로 컨테이너 열 개를 띄우고, 하나가 죽으면 다시 띄우고, 로드 밸런서 뒤에 붙이려 합니다. 이미지는 어디에 두고, 누가 개수를 유지해야 할까요?

## ECR: 이미지를 두는 창고

**ECR**(Elastic Container Registry)은 컨테이너 이미지를 태그별로 보관하는 레지스트리입니다. 빌드한 이미지를 ECR에 **푸시**하고, 실행할 곳에서 **풀**합니다. Docker Hub와 비슷하지만 AWS 권한과 함께 관리됩니다.

이미지는 수백 MB에서 수 GB라 쌓이면 용량을 차지합니다. 그렇다고 마구 지우면 새 버전에 문제가 생겼을 때 돌아갈 이전 태그가 없습니다. 최근 몇 개 태그는 남기는 수명 주기 정책을 둡니다. 프라이빗 서브넷의 서버가 ECR에서 이미지를 받으려면 NAT 게이트웨이나 VPC 엔드포인트 같은 **바깥 경로**가 필요합니다.

## ECS: 몇 개를 어디에 띄울지 관리한다

**ECS**(Elastic Container Service)는 AWS의 컨테이너 오케스트레이터입니다.

| 구성 요소 | 하는 일 |
| --- | --- |
| **태스크 정의** | 어떤 이미지로, 어떤 포트·환경 변수·권한으로 띄울지 적은 설계도. docker-compose의 AWS판 |
| **태스크** | 태스크 정의로 실제 띄운 컨테이너 묶음 |
| **서비스** | 원하는 태스크 수를 유지하고, 죽으면 다시 띄우고, ALB에 붙이고, 무중단으로 버전을 바꿈 |

## 자리를 직접 관리할까, 맡길까

| 구분 | EC2 시작 유형 | Fargate 시작 유형 |
| --- | --- | --- |
| 관리 | 직접 EC2를 띄우고 패치 | AWS가 관리(서버리스) |
| 과금 | EC2가 켜진 시간 전체 | 태스크가 요청한 CPU·메모리 × 실행 시간 |
| 시작 속도 | 이미 켜진 EC2에 얹어 빠름 | 자리를 마련하느라 조금 느림 |
| GPU·커널 접근 | 가능 | 제약이 큼 |
| 확장 | 태스크 수와 EC2 수를 모두 조절 | 태스크 수만 조절 |

EC2를 꽉 채워 쓰면 더 쌀 수 있지만 관리가 늘고, Fargate는 비싸지만 컨테이너에만 집중할 수 있습니다.

## 권한은 태스크마다 나눈다

같은 EC2에서 컨테이너 A와 B가 돌면 네트워크로는 둘을 구분하기 어렵습니다. **인스턴스 프로파일**로 권한을 주면 그 EC2의 모든 컨테이너가 권한을 공유합니다. **태스크 역할**은 태스크 정의마다 권한을 따로 주고, 호스트가 없는 **Fargate는 태스크 역할만** 쓸 수 있습니다.

## EKS: 쿠버네티스를 그대로

**EKS**(Elastic Kubernetes Service)는 관리형 쿠버네티스입니다. 앞에서 배운 Pod·Deployment·Service를 그대로 씁니다. 노드는 직접 관리, 관리형 노드 그룹, Fargate 중에서 고릅니다. ECS는 배우기 쉽고 오케스트레이터 비용이 없지만 AWS에 묶이고, EKS는 클러스터 비용과 학습 부담이 있지만 다른 클라우드나 온프레미스로 옮기기 쉽습니다.

<LessonSummary>

ECR은 이미지를 태그별로 보관하고, ECS는 태스크 정의로 태스크를 띄워 서비스가 원하는 수를 유지합니다. 자리는 직접 관리하는 EC2와 AWS가 관리하는 Fargate 중에서 고르고, 권한은 태스크 역할로 태스크마다 나눕니다. 쿠버네티스를 그대로 쓰려면 EKS를 씁니다.

- 프라이빗 서브넷에서 ECR 이미지를 받으려면 바깥 경로(NAT·엔드포인트)가 필요합니다.
- Fargate에서는 인스턴스 프로파일 대신 태스크 역할을 씁니다.

</LessonSummary>
