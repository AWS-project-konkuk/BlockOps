## 고장 난 서버에 왜 계속 요청이 갈까요?

웹 서버 세 대 중 한 대가 앱 오류로 응답하지 못합니다. 그런데 사용자 세 명 중 한 명은 계속 오류 페이지를 봅니다. 또 트래픽이 몰려 서버가 바쁜데도 서버 수는 그대로입니다. 누가 고장 난 서버를 빼고, 누가 서버를 늘려야 할까요?

## ALB: 요청을 나누는 안내 데스크

**ALB**(Application Load Balancer)는 HTTP·HTTPS 요청을 여러 대상에 나누는 L7 로드 밸런서입니다. 호스트나 경로를 보고 어느 대상으로 보낼지 정할 수도 있습니다.

| 구성 요소 | 하는 일 |
| --- | --- |
| **리스너** | 받을 포트와 프로토콜(HTTPS 443 등)을 정합니다. 리스너가 없으면 요청을 받지 않습니다. |
| **대상 그룹** | 요청을 실제로 처리할 서버 묶음입니다. |
| **헬스 체크** | 정해진 경로(`/health`)로 주기적으로 물어 건강한 대상만 남깁니다. |

헬스 체크는 **간격**마다 경로를 부르고, **비정상 임계값**만큼 연속 실패하면 Unhealthy로 판정해 요청을 끊습니다. 앞의 문제는 헬스 체크 경로를 앱에 없는 주소로 잘못 적었거나 헬스 체크가 없어서, 고장 난 서버를 걸러 내지 못한 경우입니다.

## Auto Scaling 그룹: 수를 맞추고 교체하는 관리자

**Auto Scaling 그룹**(ASG)은 같은 설정의 EC2를 원하는 수만큼 유지합니다. 어떤 설정으로 띄울지는 **Launch Template**에 적습니다. AMI, 인스턴스 유형, 보안 그룹, 서브넷, 시작 스크립트(User Data)가 들어가고, 버전을 남겨 두면 새 버전에 문제가 있을 때 이전 버전으로 돌아갈 수 있습니다.

| 설정 | 의미 |
| --- | --- |
| 최소 | 아무리 한가해도 유지할 수 |
| 원하는 수 | 평소에 유지할 수 |
| 최대 | 몰려도 넘기지 않는 수. 비용 상한 |

**조정 정책**은 언제 늘리고 줄일지 정합니다. **대상 추적**은 "CPU 50% 유지"처럼 목표를 주면 알아서 맞추고, **단계 조정**은 구간별로 몇 대씩 늘릴지 정하고, **예약 조정**은 출근 시간처럼 정해진 시각에 미리 늘립니다. 인스턴스가 뜨는 데 시간이 걸리므로 조정 사이에는 **Cooldown**을 둡니다.

## 둘이 맞물리는 방식

1. ASG가 새 EC2를 띄우면 대상 그룹에 자동으로 등록합니다.
2. ALB의 헬스 체크가 Unhealthy로 판정하면 요청을 끊고, ASG는 그 인스턴스를 종료한 뒤 새로 띄웁니다.
3. 새 인스턴스가 Healthy가 되면 ALB가 요청을 보내기 시작합니다.

보안 그룹은 **체이닝**으로 묶습니다. EC2의 보안 그룹은 "ALB 보안 그룹에서 오는 요청만 허용"으로 두면, 인스턴스가 몇 대가 되든 규칙을 고칠 필요가 없고 인터넷에서 EC2로 바로 오는 길도 막힙니다. 그래서 ASG의 인스턴스는 프라이빗 서브넷에 둡니다.

<LessonSummary>

ALB는 리스너로 요청을 받아 헬스 체크를 통과한 대상 그룹의 서버에만 나눠 줍니다. Auto Scaling 그룹은 Launch Template으로 서버를 띄우고 최소·원하는 수·최대 사이에서 수를 조절하며, Unhealthy 서버를 교체합니다. 두 서비스가 맞물려 수평 확장과 자동 복구를 함께 해냅니다.

- 고장 난 서버에 요청이 가면 헬스 체크 경로와 임계값을 확인합니다.
- 서버가 늘지 않으면 조정 정책과 최대 수를 확인합니다.

</LessonSummary>
