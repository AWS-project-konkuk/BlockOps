## 웹 서버는 살았는데 DB가 멈췄다면?

웹 서버를 두 가용 영역에 나눠 두어서, 한 영역이 멈춰도 웹 페이지는 열립니다. 그런데 주문 버튼을 누르면 오류가 납니다. DB가 멈춘 영역에 한 대만 있었기 때문입니다. DB도 웹 서버처럼 여러 대로 늘리면 될까요?

## DB는 EC2에서 떼어 낸다

EC2에 DB를 직접 설치하면 백업, 패치, 장애 복구를 모두 직접 해야 하고, 서버가 멈추면 데이터도 함께 위험해집니다. **RDS**(Relational Database Service)는 MySQL, PostgreSQL 같은 관계형 DB를 관리형으로 제공합니다. DB를 앱 서버에서 분리하는 것은 인프라의 기본입니다.

RDS는 **DB 서브넷 그룹**으로 어느 서브넷에 둘지 정합니다. 보통 두 가용 영역의 프라이빗 서브넷을 묶습니다. 인터넷 경로가 있는 퍼블릭 서브넷에 두면 DB가 외부에 노출될 수 있습니다.

## Multi-AZ와 읽기 복제본은 목적이 다르다

| 구분 | Multi-AZ | 읽기 복제본 |
| --- | --- | --- |
| 목적 | 고가용성(장애 대비) | 확장성(읽기 분산) |
| 복제 방식 | 동기: 데이터가 항상 같음 | 비동기: 조금 늦을 수 있음 |
| 평소 사용 | 대기 DB는 요청을 받지 않음 | 읽기 요청을 받음 |
| 장애 시 | 대기 DB가 자동으로 메인이 됨 | 직접 승격해야 함 |
| 비용 | 인스턴스 두 대 | 추가한 수만큼 |

앞의 주문 오류는 **Multi-AZ**로 풉니다. 메인 DB의 가용 영역이 멈추면 다른 영역의 대기 DB가 자동으로 승격되고, 앱은 같은 엔드포인트로 계속 접속합니다.

반대로 상품 조회처럼 읽기 요청이 많아 메인 DB가 바쁘다면 **읽기 복제본**을 둡니다. 조회는 복제본으로, 주문 같은 쓰기는 메인으로 보냅니다. 복제본은 조금 늦게 따라오므로 방금 쓴 값을 바로 읽어야 하는 요청은 메인으로 보냅니다.

## 보안 그룹은 앱 쪽에서 들어오는 것만

앱이 DB에 쿼리를 보내므로 **앱이 클라이언트, DB가 서버**입니다. DB의 보안 그룹 인바운드에 "앱 서버 보안 그룹에서 오는 DB 포트"만 허용합니다. 보안 그룹은 Stateful이라 응답은 따로 열 필요가 없습니다.

<LessonSummary>

RDS는 관리형 관계형 DB로, 앱 서버와 분리해 프라이빗 서브넷에 둡니다. Multi-AZ는 다른 가용 영역에 동기 복제한 대기 DB를 두어 장애 때 자동 승격하고, 읽기 복제본은 비동기 복제로 읽기 요청을 나눕니다. 가용성 문제에는 Multi-AZ, 읽기 부하 문제에는 읽기 복제본을 씁니다.

- DB의 보안 그룹은 앱 서버의 보안 그룹에서 오는 DB 포트만 허용합니다.
- 읽기 복제본은 늦을 수 있으므로 방금 쓴 값을 읽는 요청은 메인 DB로 보냅니다.

</LessonSummary>
