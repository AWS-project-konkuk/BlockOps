## 테스트를 건너뛴 이미지가 운영에 나갔다면?

배포 날, 담당자가 노트북에서 이미지를 빌드해 ECR에 올렸습니다. 급한 마음에 테스트를 건너뛰었고, 그 이미지가 운영에 나가 주문이 멈췄습니다. 사람이 매번 같은 순서를 지키게 하는 대신, 순서를 자동으로 강제할 수는 없을까요?

## CI와 CD

- **CI**(지속적 통합): 커밋이나 PR마다 자동으로 빌드하고 테스트합니다. 문제가 있는 변경이 합쳐지기 전에 걸러 냅니다.
- **CD**(지속적 배포): CI를 통과한 결과물을 자동으로 배포 가능한 상태로 만들거나, 운영까지 배포합니다.

핵심은 **앞 단계가 실패하면 뒤 단계로 가지 않는다**는 것입니다. 테스트가 실패하면 빌드도, 이미지 푸시도, 배포도 일어나지 않습니다.

## GitHub Actions로 만드는 파이프라인

**GitHub Actions**는 저장소의 이벤트(push, pull_request)에 맞춰 **워크플로**를 실행합니다. 워크플로는 `.github/workflows/`의 YAML 파일에 적고, 잡(job)과 단계(step)로 이루어집니다.

| 이벤트 | 단계 | 결과 |
| --- | --- | --- |
| PR 열림 | 설치 → 린트 → 테스트 → 빌드 | 통과 여부를 PR에 표시 |
| main 병합 | 테스트 → 이미지 빌드 → ECR 푸시 | 커밋 태그가 붙은 이미지 |
| 배포 승인 | ECS 서비스의 태스크 정의를 새 이미지로 갱신 | 새 버전 배포 |

PR에서는 통과한 단계도 main 병합 때만 도는 단계(이미지 게시, 시크릿 사용)는 따로 확인해야 합니다. 시크릿과 환경 변수는 저장소에 적지 않고 GitHub Secrets에 둡니다.

## 이미지 태그와 되돌리기

이미지에 `latest`만 붙이면 지금 운영에 어떤 커밋이 나가 있는지 알 수 없고, 문제가 생겼을 때 돌아갈 버전도 모릅니다. 커밋 해시나 `v1.2.3`처럼 버전으로 태그를 붙이고, ECR에 이전 태그를 남겨 둡니다.

새 이미지를 운영에 **어떻게 바꿔 넣을지**는 다음 강의들의 배포 전략(중단 배포, Blue·Green, Canary, Shadow)이 다룹니다.

<LessonSummary>

CI는 커밋마다 자동으로 빌드·테스트해 문제 있는 변경을 걸러 내고, CD는 통과한 결과물을 배포까지 이어 줍니다. GitHub Actions는 저장소 이벤트에 맞춰 워크플로를 실행하고, 앞 단계가 실패하면 뒤 단계로 가지 않습니다. 이미지에는 커밋이나 버전 태그를 붙여 무엇이 배포됐는지 알고 되돌릴 수 있게 합니다.

- main 병합 때만 도는 단계의 시크릿·환경 변수는 PR 통과와 별도로 확인합니다.
- 운영으로 바꿔 넣는 방법은 배포 전략으로 고릅니다.

</LessonSummary>
