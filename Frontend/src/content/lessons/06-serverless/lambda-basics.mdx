## 하루 다섯 번 쓰는 기능 때문에 서버를 24시간 켜야 할까요?

## 모놀리식에서 서버리스까지

예전 웹 애플리케이션은 모든 기능을 하나로 묶은 **모놀리식**이었습니다. 결제만 바빠도 로그인·메인 화면까지 통째로 늘려야 했죠. 기능을 쪼개 독립 서버로 만든 **마이크로서비스**(MSA)는 필요한 기능만 늘릴 수 있지만, 관리할 서버가 기능 수만큼 늘어났습니다. 거의 쓰이지 않는 기능도 언제 쓰일지 몰라 켜 둬야 했습니다.

**서버리스**는 서버를 직접 관리하지 않는 방식입니다. 서버가 없는 것은 아니지만, 띄우고 패치하고 늘리는 일은 AWS가 합니다. 이미 만들어진 기능(DB, 인증)을 API로 쓰는 것이 **BaaS**, 내가 쓴 함수를 이벤트마다 실행하는 것이 **FaaS**입니다. AWS의 FaaS가 **Lambda**입니다.

## Lambda는 이렇게 동작한다

1. 코드를 **함수**로 올립니다. 함수는 하나의 일을 합니다.
2. **트리거**(API Gateway 요청, S3 업로드, SQS 메시지, 정해진 일정)가 이벤트를 JSON으로 보냅니다.
3. Lambda가 언어별 **런타임**(Node.js, Python, Java 등)에서 **핸들러**를 부르고, 핸들러는 이벤트를 받아 처리합니다.
4. 함수가 다른 AWS 서비스에 접근할 권한은 **실행 역할**로 줍니다.

여러 함수가 쓰는 라이브러리는 **계층**(Layer)으로 분리해 배포 패키지를 작게 유지합니다.

## 첫 요청만 느린 이유

처음이거나 오랫동안 호출되지 않은 함수는 격리 환경을 만들고 런타임을 띄우고 코드를 받아야 합니다. 이것이 **콜드 스타트**입니다. 한 번 실행된 환경이 남아 있으면 핸들러만 다시 부르는 **웜 스타트**라 빠릅니다. Java처럼 무거운 런타임은 콜드 스타트가 길어서, 짧고 자주 불리는 함수는 Node.js나 Python으로 만드는 경우가 많습니다.

## 쓴 만큼만 낸다

Lambda의 비용은 **요청 수**와 **실행 시간(메모리 × 시간)**으로 정해집니다. 쿠폰 발급처럼 드물게 쓰는 기능은 서버를 켜 두는 것보다 훨씬 쌉니다. 반대로 하루 종일 쉬지 않고 바쁜 기능은 오히려 서버나 컨테이너가 쌀 수 있습니다. 표준 함수는 최대 15분까지 실행됩니다.

<LessonSummary>

서버리스는 서버 관리를 AWS에 맡기고 코드에 집중하는 방식이고, Lambda는 이벤트가 올 때만 함수를 실행하는 FaaS입니다. 트리거가 보낸 이벤트를 런타임의 핸들러가 받아 처리하고, 실행 역할로 권한을 받습니다. 오랜만의 첫 호출은 콜드 스타트로 느리고, 비용은 요청 수와 실행 시간만큼 냅니다.

- 드물게 쓰거나 이벤트로 시작하는 일은 Lambda, 쉬지 않고 바쁜 일은 서버·컨테이너가 맞을 수 있습니다.
- 짧고 자주 불리는 함수는 가벼운 런타임으로 콜드 스타트를 줄입니다.

</LessonSummary>
