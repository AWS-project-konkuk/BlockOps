## 서버 없이 주문 API를 만들려면 무엇이 더 필요할까요?

Lambda로 주문을 저장하는 함수를 만들었습니다. 그런데 사용자의 앱은 `POST /orders`라는 HTTP 주소로 요청합니다. 함수는 HTTP 주소가 없고, 주문을 저장할 곳도 정해야 합니다. 서버 없이 이 둘을 어떻게 채울까요?

## API Gateway: HTTP 요청의 입구

**API Gateway**는 HTTP 요청을 받아 Lambda 같은 통합 대상을 부릅니다. 인증, 요청 수 제한, 경로별 라우팅을 맡아서 함수는 처리에만 집중합니다.

| 구분 | HTTP API | REST API |
| --- | --- | --- |
| 비용 | 약 70% 저렴 | 상대적으로 비쌈 |
| 지연 | 매우 낮음 | 조금 더 큼 |
| 기능 | 핵심만 (캐싱·요청 변환·웹소켓 없음) | API Gateway 기능 전부 |
| 어울리는 곳 | Lambda 기반 서버리스 API | 복잡한 기업용 API |

특별한 기능이 필요 없으면 HTTP API를 씁니다.

## DynamoDB: 키로 찾는 NoSQL

**DynamoDB**는 10밀리초 이하로 응답하는 서버리스 NoSQL 데이터베이스입니다. 서버를 띄우지 않고 읽기·쓰기 양만큼 냅니다. 데이터는 **테이블 → 항목 → 속성**으로 이루어지고, 테이블을 만들 때 **기본 키**를 정합니다.

- **파티션 키**만 쓰기: 값의 해시로 저장할 파티션(물리적 위치)을 정합니다. 키는 겹치면 안 됩니다.
- **파티션 키 + 정렬 키**: 같은 파티션 키 안에서 정렬 키로 구분하고 빠르게 찾습니다.

파티션 키는 **고르게 퍼지는 값**이어야 합니다. 주문 날짜를 키로 쓰면 오늘 주문이 모두 한 파티션에 몰리는 **핫 파티션**이 되어, 그 파티션의 처리량을 넘는 순간 쓰기가 거절됩니다. 주문 ID처럼 다양한 값을 씁니다.

## 용량과 일관성, 그리고 부가 기능

| 항목 | 내용 |
| --- | --- |
| 용량 모드 | 온디맨드(쓰는 만큼) 또는 프로비저닝(RCU·WCU를 미리 정함) |
| RCU·WCU | 읽기 1 RCU = 강력한 일관성 1회 또는 최종 일관성 2회(4KB까지), 쓰기 1 WCU = 1KB 쓰기 1회 |
| 읽기 일관성 | 최종 일관성은 빠르고 싸지만 잠깐 예전 값을 볼 수 있음. 은행 잔고·재고는 강력한 일관성 |
| Streams | 항목이 바뀔 때마다 기록을 남기고 Lambda를 트리거할 수 있음 |
| TTL | 만료 시각이 지난 항목을 자동으로 지움 |

<LessonSummary>

API Gateway는 HTTP 요청을 받아 Lambda를 부르는 입구이고, 특별한 기능이 필요 없으면 저렴한 HTTP API를 씁니다. DynamoDB는 파티션 키의 해시로 저장 위치를 정하는 서버리스 NoSQL이라, 키가 한 값에 몰리면 핫 파티션이 됩니다. 용량 모드와 읽기 일관성은 비용과 정확성 사이에서 고릅니다.

- 파티션 키는 주문 ID처럼 고르게 퍼지는 값으로 정합니다.
- Streams와 Lambda를 이으면 데이터가 바뀔 때마다 후속 작업을 실행할 수 있습니다.

</LessonSummary>
