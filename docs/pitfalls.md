# BlockML에서 반복된 실수

BlockML(AWS_project)의 PR 57개, 이슈 25개, 리뷰 코멘트에서 실제로 문제가 됐던 것만 모았습니다. 작업 전에 해당 분야를 읽고, PR을 올리기 전에 맨 아래 체크리스트를 확인합니다. 괄호 안 번호는 AWS_project의 이슈·PR 번호입니다.

## 1. 배포 환경은 로컬과 다르다

로컬 개발 서버는 `localhost`라서 HTTPS와 같은 "보안 컨텍스트"로 취급됩니다. 배포 환경은 HTTP이고 `/container-3/` 같은 하위 경로 아래에서 돌아갑니다. 로컬에서 되는 기능이 배포에서만 깨진 경우가 가장 많았습니다.

| 하지 말 것 | 대신 할 것 | 사례 |
|---|---|---|
| `crypto.randomUUID()`, `crypto.subtle` 직접 호출 | `Frontend/src/ids.ts`의 `newId()` | HTTP에서 노드 추가·실습 실행이 멈춤 (#12, PR #72) |
| `navigator.clipboard` 직접 호출 | `Frontend/src/clipboard.ts`의 복사 함수 | HTTP에서 워크플로우 ID 복사 실패 (#71, PR #82) |
| 이미지·정적 파일을 `/images/...`처럼 절대 경로로 참조 | `images/...` 상대 경로. Vite는 `base: './'` | 하위 경로 배포에서 레슨 이미지가 안 보임 (#74, PR #75) |
| 로컬에서 됐으니 배포도 된다고 판단 | HTTP 환경을 흉내 내는 `tests/e2e/insecure-context.spec.ts` 방식으로 테스트하고, PR에 "배포 후 확인할 것"을 적은 뒤 실제로 확인 | PR #72, #75, #82 |

새 브라우저 API를 쓸 때는 [MDN](https://developer.mozilla.org/)에서 "Secure context" 표시가 있는지 먼저 확인합니다.

## 2. 프론트엔드와 백엔드의 데이터 형식을 따로 가정하지 않는다

| 하지 말 것 | 대신 할 것 | 사례 |
|---|---|---|
| 백엔드 검증 테스트에 손으로 만든 샘플 JSON 사용 | 프론트엔드가 실제로 보내는 형식으로 테스트 데이터 작성 | 테스트는 `root`의 `parent`를 `"root"`로 적었지만, 실제 프론트는 `""`를 보내서 배포에서 모든 워크플로우 업로드가 400 (PR #77) |
| 그래프 구조를 바꾸면서 저장된 게시글은 신경 쓰지 않기 | 구조를 바꾸면 워크플로우 `version`을 올리고, 프론트 `readWorkflow`와 백엔드 `WorkflowValidator`를 같은 PR에서 함께 수정. 기존 데이터를 변환할지 거부할지 결정 | 구조 변경 뒤 게시글 불러오기가 깨져서 게시글을 전부 다시 만듦 (#60, #73) |
| 프론트에서 서버 검증 규칙을 한 번 더 구현 | 검증 규칙은 서버 한 곳에 두고, 프론트는 서버의 `code`·`message`를 그대로 안내 | 규칙이 두 곳에 생겨서 나중에 프론트 사전 검증을 걷어냄 (PR #80 이후) |
| 실패를 전부 400으로 반환 | 형식 오류 400, 요건 미달 422처럼 구분 | PR #79 |
| 데이터가 없을 때 200과 빈 body 반환 | 404 등 명확한 상태 코드 | PR #20 리뷰 |
| 목록 API에서 본문·큰 JSON까지 반환, 페이지 크기를 코드에 숫자로 고정 | 목록용 DTO는 필요한 필드만 반환하고, 페이지 크기는 설정으로 분리 | PR #20, #27 리뷰 |

## 3. CI와 배포

| 하지 말 것 | 대신 할 것 | 사례 |
|---|---|---|
| PR에서 CI가 통과했으니 main도 통과한다고 가정 | `push: main`에서만 도는 단계(이미지 게시 등)의 환경 변수·시크릿을 따로 확인 | main 병합 후 게시 단계에 환경 변수가 없어 실패 (PR #19) |
| 외부 DB에 연결해야 통과하는 테스트를 CI에 넣기 | 외부 연결이 필요한 테스트는 빼거나 대체 | DB 연결 테스트가 CI를 깨뜨려서 삭제 (#62, PR #76) |
| GHCR 이미지가 공개 상태라고 가정 | 새 패키지는 기본이 Private. EKS에서 받으려면 Public으로 전환 | #66 |
| 리소스 quota를 보지 않고 replica 수 결정 | Pod의 requests·limits와 네임스페이스 quota로 실제로 몇 개가 뜨는지 계산 | quota 때문에 replica 3개 중 2개만 뜸 (PR #28) |
| 백엔드 HTTP 클라이언트 기본 설정 그대로 사용 | vLLM 호출은 HTTP/1.1로 고정 | `Unsupported upgrade request`·400 반복 (PR #10) |

## 4. 강의 콘텐츠

| 하지 말 것 | 대신 할 것 | 사례 |
|---|---|---|
| `**포인터(pointer)**입니다`처럼 굵은 글씨 안에 괄호를 넣고 바로 조사 붙이기 | `**포인터**(pointer)입니다` 또는 `<strong>포인터(pointer)</strong>입니다` | 별표가 그대로 보임 (#36, PR #40) |
| "아래 그림", "아래 관계를 완성하세요"라고 쓰고 실제 화면 확인 안 하기 | 브라우저에서 렌더링된 페이지를 직접 보고 확인 | 그림이 위로 옮겨져 문장과 어긋남 (PR #16 리뷰) |
| 요약(`summary`), 시나리오(`scenario`), 인트로를 비슷한 문장으로 쓰기 | 요약은 한 줄 정리, 시나리오는 구체적인 상황, 인트로는 문제를 바로 느끼게 하는 질문으로 역할을 나눔 | #47 |
| 임시 그림을 넣고 공유하지 않기 | 임시 자료는 이슈로 남기고 PR 본문에 적기 | #45, PR #41 리뷰 |
| 학습자가 안다고 가정하고 용어를 설명 없이 쓰기 | 처음 나오는 용어는 본문에서 정의 | PR #41 리뷰(마이크로배치) |
| 실습을 만들고 직접 해 보지 않기 | 값의 범위가 화면에 다 보이는지, 결과가 직관적으로 변하는지 직접 조작해 확인 | #44, #46 |
| 다른 사람이 콘텐츠를 고치는 동안 레슨 번호·폴더 일괄 변경 | 콘텐츠 작업이 없을 때 번호를 바꾸고, 폴더 번호와 단원 번호를 일치시킴 | 충돌 우려로 PR #15 닫음. `02-runtime`이 실제로는 1단원이라 혼동 (PR #11 리뷰) |

## 5. 협업

| 하지 말 것 | 대신 할 것 | 사례 |
|---|---|---|
| 작업 종류와 맞지 않는 PR 제목 접두사 | 제목 접두사가 라벨을 정함(`.github/workflows/pr-title-labels.yml`). 쓸 수 있는 접두사는 `feat`, `fix`, `hotfix`, `chore`, `build`, `ci`, `refactor`, `test`. 테스트만 추가하면 `test` | PR #22 |
| `.vscode` 같은 개인 설정 커밋 | 공유 목적이 아니면 `.gitignore` | PR #20 리뷰 |
| 다른 PR 위에 쌓은 PR을 말없이 올리기, 잘못된 브랜치에서 PR | 선행 PR을 본문에 적고, PR 전 base 브랜치 확인 | PR #59, #64 |
| 환경 변수를 추가하고 예시 파일은 그대로 두기 | `.env.example`에 키와 예시 값 추가 | PR #14 |
| 리뷰 논의가 길어진 PR을 계속 붙잡고 있기 | 병합 후 남은 논의는 이슈로 분리 | PR #20 |
| 구조 변경(단원 통합 등)을 혼자 결정하고 공유하지 않기 | 이슈나 PR 본문으로 팀에 공유 | PR #11 리뷰 |

## 6. AI 조언 (아직 해결되지 않은 문제)

BlockOps에서 프롬프트를 바꿀 때(#6) 같이 다룹니다.

- 첫 요청이 거의 항상 실패함. 연결 준비 시간 때문으로 추정 (#38)
- 답안 평가가 너무 엄격해서 배우지 않은 내용까지 요구함. 배운 범위 안에서 평가하고 부족한 점은 보충 설명으로 안내해야 함 (#56)
- 노드 실습 조언이 "아키텍처 검증"처럼 형식적임. 요청에 실습별 개념 정보를 넣어야 함 (#57, #58)
